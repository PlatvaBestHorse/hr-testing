# Резервные копии и восстановление

Код в GitHub и ZIP исходников не содержат PostgreSQL. Команды ниже создают **полную копию локальной dev-базы всех организаций**, включая пользователей, кандидатов, вопросы, ответы, результаты, аудит, согласия и правила хранения. Это операторские команды, а не функции кабинета HR. Доступ к Docker и паролю владельца схемы нужен только оператору среды. Для отдельной production-базы используется тот же проверяемый шифрованный формат через другую штатную команду: [operations.md](operations.md), включая реплику/расписание/контроль.

## Создать и проверить

В облачной среде из `/workspace/hr-testing` сначала активируйте инструменты:

```bash
. scripts/cloud_env.sh
make backup
make backup-list
make backup-verify
```

`make backup` использует `pg_dump` PostgreSQL 17 из работающего Compose-контейнера. Снимок PostgreSQL экспортируется из read-only repeatable-read транзакции: дамп и контрольные суммы относятся к одному состоянию базы даже при работе API. Для каждой таблицы записываются количество строк и SHA-256 отсортированного JSON содержимого. JSON приводится к UTC и ISO DateStyle. На больших базах сортировка требует времени и временного пространства PostgreSQL; текущий инструмент рассчитан на локальный контур, с общим таймаутом 30 минут.

Дамп идёт через память прямо в шифрование, без незашифрованного файла на диске. Формат HRBACKUP1 использует AES-256-GCM, случайный 128-битный идентификатор архива и отдельный ключ архива через HMAC-SHA256. Записи по 64 КиБ проверяют последовательность и длину, финальная аутентифицированная запись защищает от обрезания. Неверный ключ, повреждение, перестановка записей и дописанные байты приводят к отказу.

**До появления готового файла команда действительно восстанавливает копию в отдельную случайную базу `hr_restorecheck_*`.** Сравниваются точное содержимое всех таблиц, номера и SHA-256 применённых миграций, права `hr_app` и пять триггеров неизменяемости. Проверяется реальный отказ на UPDATE/DELETE аудита и, при наличии опубликованных версий, отказ на изменение вопросов/тестов. Проверка не применяет новые миграции автоматически. Временная база удаляется, затем готовый зашифрованный файл атомарно появляется в `.backups/hr-*.hrbak`. При ошибке готовая копия не публикуется. Если удалить проверочную базу не удалось, команда сообщает её имя и завершается ошибкой; оператор должен убрать её отдельно.

Каталог `.backups` имеет права 0700, файлы — 0600. Незавершённые файлы `.incomplete-*` не считаются копиями; обычный отказ удаляет их, аварийное прекращение процесса может оставить зашифрованный остаток. Существующая база и настройки подключения API не заменяются. Одновременно с резервным копированием не меняйте схему, роли и ACL; операции над данными допускаются.

`make backup-verify` повторяет восстановление последнего по имени файла. Можно выбрать копию:

```bash
make backup-verify FILE=.backups/hr-YYYYMMDDTHHMMSSZ-ID.hrbak
```

Имена используют UTC. Если копии созданы в одну секунду, выбирайте конкретный файл: порядок случайного суффикса не означает порядок создания. `make backup-list` проверяет аутентичность всех копий и показывает время из защищённого содержимого.

## Ключ и независимое хранение

При первой копии генерируется случайный 32-байтовый ключ `.env.backup.key` с правами 0600. Повторный запуск использует его без замены. Если ключ исчез, а копии остались, команда отказывается генерировать новый. Можно указать другой защищённый файл через `HR_BACKUP_KEY_FILE`.

**Потеря ключа означает потерю доступа ко всем копиям.** Сохраните ключ отдельно в защищённом хранилище организации, а зашифрованные копии — вне машины, где работает PostgreSQL. Не отправляйте ключ в чат, не включайте его в ZIP исходников, GitHub и инструкции. `.env.backup.key` и `.backups/` исключены из Git. Локальная копия на той же машине защищает от ошибки в базе, но не от потери всей машины. Внешнее хранилище, расписание и оповещения в этом этапе не подключены.

Роли PostgreSQL и их пароли не входят в дамп базы (`pg_dump`, а не `pg_dumpall`). Для новой машины подготовьте PostgreSQL 17, прежнюю роль владельца и ограниченную `hr_app` через штатный Compose/init; берегите конфигурацию отдельно. Пароли не переносите публично. `--no-owner` назначает восстановленные объекты текущему владельцу, **ACL сохраняются**; `--no-acl` не используется.

## Правила хранения копий

Удаление вручную, расписания и срока по умолчанию нет. Период задаёт оператор по утверждённой политике организации; пример 30 дней — не юридическая рекомендация.

```bash
make backup-prune DAYS=30                           # только предпросмотр
make backup-prune DAYS=30 APPLY=DELETE_OLD_BACKUPS   # применить
```

Период 1–36500 дней считается по 24 часа от защищённого времени снимка, а не по дате изменения файла. Перед удалением проверяются все архивы; повреждённый, открытый другим пользователям или символьная ссылка останавливают операцию до первого удаления. Самая новая по времени снимка копия сохраняется независимо от возраста. При файловой ошибке удаления уже удалённые копии не возвращаются, команда сообщает о частичном выполнении. Ключ не удаляется. Правила `/retention` очищают данные базы и не управляют файлами копий.

## Восстановить в отдельную базу для оператора

```bash
python3 scripts/run_backend.py backup restore \
  --file .backups/hr-YYYYMMDDTHHMMSSZ-ID.hrbak \
  --target hr_recovery_manual \
  --ledger /защищённый/путь/актуальный.hrledger \
  --confirm CURRENT_ERASURE_LEDGER
```

Финальный экспорт реестра, восстановление и переключение выполняйте при остановленных изменениях исходной линии в окно обслуживания: новая запись удаления после сверки потребует новой сверки. Команда создаёт **новую** базу с именем `hr_recovery_` и суффиксом из строчных латинских букв, цифр или подчёркивания (1–32 символа). Существующая база не перезаписывается; `--clean` и выбор рабочей базы не поддерживаются. Повреждённый архив отклоняется до создания базы. При ошибке созданная база удаляется; при успехе остаётся для оператора, API продолжает использовать прежнюю.

После точной проверки снимка восстановление удаляет старые сессии, предпросмотры очистки, токены восстановления/приглашений сотрудников и связанную очередь писем, резервные коды MFA и незавершённые настройки MFA; отзывает приглашения кандидатов и отменяет ожидающие/неудачные почтовые сообщения. При переходе на восстановленную базу пользователям потребуется новый вход и новые ссылки. Действующий MFA остаётся включённым; зашифрованный TOTP-ключ сохраняется, счётчик использованного шага не откатывается до доступного к повтору кода. Нужен **исходный `AUTH_ENCRYPTION_KEY`**, хранимый отдельно от базы и ключа архивов. Пользователи входят с приложением-аутентификатором и выпускают новые резервные коды; старые коды из снимка не возобновляются. Без приложения и кодов потребуется отдельная операторская процедура проверки личности.

В режиме `verify` такой обработки нет: он сравнивает исходный снимок и удаляет всю проверочную базу.

Перед переходом на восстановленную базу:

1. Остановите доступ API/кандидатов и почтовых отправителей; сохраните текущую базу отдельной копией, если она доступна.
2. Проверьте восстановление командой выше и сопоставьте результаты с нужной датой снимка. Сохраните старые данные до решения оператора.
3. **Повторно примените удаления, исправления контактов и запреты, произошедшие после снимка.** Возврат старой копии может вернуть ранее удалённые персональные данные. Восстановленные предпросмотры сброшены, поэтому для повторной очистки создавайте новые. Не включайте API до сверки с независимым учётом запросов на удаление организации. Зашифрованный экспорт реестра теперь поддерживается; автоматическое внешнее хранение ещё не подключено. Оставляемое восстановление повторно применяет реестр, но более поздние исправления контактов/запретов и полноту внешней копии проверяет оператор.
4. Подготовьте отдельное подключение ограниченной роли `hr_app` к новой базе. Используйте защищённые настройки Compose в изолированном контуре; не подменяйте только POSTGRES_DB у существующего PG-каталога — init-скрипт не создаст роли повторно.
5. Выполните `/readyz`, вход администратора, просмотр отчёта и выдачу новой тестовой ссылки. После проверки оператор переключает приложение в своё окно обслуживания. Автоматического переключения этим инструментом нет.

Изображения заданий хранятся в attachments.data в PostgreSQL и входят в эту же копию и проверку содержимого. Проверяются пять триггеров, включая неизменяемость вложения. Текущая схема содержит 15 миграций и 40 таблиц. Старые копии схем до 0015 проверяйте соответствующим выпуском проекта: текущий CLI требует точное соответствие миграций и не обновляет восстановленную схему автоматически. Исходные старые копии сохраняются.

Инструмент не является восстановлением на любой момент времени (WAL/PITR), не копирует будущие внешние файлы/объектное хранилище и не предназначен для удалённого PostgreSQL. Для промышленной эксплуатации требуются внешнее хранение, отдельный контроль доступов, согласованные RPO/RTO и регулярные проверки в изолированной среде.

## Проверки разработчика

`make check` включает тесты поточного формата: размеры на границе блока, неверный ключ, обрезание, изменение заголовка/данных, перестановка, дописывание и ошибки I/O. Тесты CLI проверяют сохранение ключа, отказ замены потерянного ключа, предпросмотр хранения, сохранение последней копии, повреждённые файлы и права 0600.

`make integration` также запускает `cmd/backup`: создаёт собственную временную базу, миграции и фикстуры, создаёт/восстанавливает копию, проверяет оставляемую recovery-базу, отмену старых сессий/сообщений/ссылок/резервных кодов, сохранение активного MFA и расшифровку исходным ключом, отказ перезаписи и повреждённого архива. Чистит только созданные базы. Не запускайте интеграцию на промышленном PostgreSQL.

Квитанции импорта и связи исходных ID входят в копию PostgreSQL (миграция 0013); повторная загрузка после восстановления распознаётся. Исходные JSON-файлы `.imports/` в дамп базы не входят: храните их отдельную защищённую копию с контрольной суммой.


С миграции 0015 оставляемое восстановление требует актуальный независимый зашифрованный реестр удалений. Экспорт: make backup-ledger (после первой копии/ключа), после каждого удаления обоих типов. Реестр содержит только UUID/scope/время; приложение не может менять/удалять записи. Restore проверяет его аутентичность, свежесть относительно снимка и линию базы, затем повторяет очистку контактов/полное удаление. Если исходная линия доступна, экспорт должен точно соответствовать её реестру. При утрате исходной линии полноту подтверждает оператор: флаг CURRENT_ERASURE_LEDGER — не техническое доказательство полноты. Внешняя доставка/расписание ещё не включены на реальном сервере; production-команда того же CLI и подготовка реплики описаны в [operations.md](operations.md). Команды make из этой инструкции относятся к dev Compose. Подробности и ограничения — [personal-data.md](personal-data.md).
