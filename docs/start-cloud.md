# Запуск облачной среды Кадрового тестера

Используйте существующую рабочую копию `/workspace/hr-testing`. Каждая облачная задача уже изолирована; не создавайте Git worktree без запроса пользователя. Основной репозиторий — PlatvaBestHorse/hr-testing, рабочая ветка HR-TESTING. Пользователь разрешил выгрузку текущего проекта в эту ветку. Для последующих изменений выполняйте push только по явному запросу пользователя; используйте обычный push с сохранением удалённой истории. Файлы, зависимости и база сохраняются отдельно от процессов, которые надо запускать после восстановления среды.

1. Из `/workspace/hr-testing` выполните `. scripts/cloud_env.sh`. Активируются Go 1.26.9, доступные кэши, Docker buildx, предоставленный сетевой прокси и проверяемый системный CA-bundle для сборок. Используйте Node.js 24 и Docker Compose. Не выводите значения `.env`, `.env.admin.json` или переменных секретов.
2. Выполните `make up`. Команда сохраняет `.env`, запускает PostgreSQL, применяет миграции владельцем схемы, затем запускает API ограниченной ролью и интерфейс. Не удаляйте `.local/postgres`, не сбрасывайте локальные пользовательские пароли и не меняйте DB-пароли только через `.env`.
3. Локальные запросы к API `/readyz` на порту 8080 и к интерфейсу `/api/v1/status` на 8088 должны вернуть `{"status":"ready"}`. HTML `/login` на 8088 должен содержать заголовок «Кадровый тестер». Наличие порта/контейнера само по себе не доказывает работу приложения. На ошибках смотрите логи только соответствующих сервисов; не выводите docker compose config или полный docker inspect с секретами.
4. В подготовленной базе есть одна организация и тестовый администратор. Его уникальный пароль сохранён в `.env.admin.json` с правами 0600. Bootstrap повторно не нужен. Вход — `/login`; текущие роли/организация/CSRF возвращаются `/api/v1/me`. Браузерные тесты используют этот файл напрямую, не печатая значения. Если файла нет, не выдумывайте пароль существующего аккаунта и не сбрасывайте его. На действительно пустой локальной базе после миграций используйте `make admin` с интерактивным защищённым вводом; `make admin-dev` допустим только в локальном тестовом контуре. В текущем процессе cookie Secure явно отключён для loopback HTTP. Для HTTPS требуется COOKIE_SECURE=true и APP_ORIGINS с точным HTTPS-origin.
5. Проверки разработки: `make check` и `make integration` из корня; `npm run test:e2e` из `frontend` при работающих контейнерах. Для Chromium используется `/usr/bin/chromium`. Обычный Go test без TEST_DATABASE_URL пропускает DB/HTTP-интеграцию, поэтому не подменяет make integration. make integration создаёт отдельную случайную hr_integration_* базу в локальном Compose PostgreSQL, применяет миграции, запускает DB/HTTP/CLI-проверки и удаляет только эту базу. Внутри тестов остаются временные организации/вложенные backup-базы с отдельной очисткой. Не подменяйте TEST_DATABASE_URL адресом основной базы: фиктивные mail-ключи/worker тестов не должны читать рабочую очередь. Не используйте production-базу. Браузерные проверки оставляют помеченные вопросы, тесты, кандидатов, вакансии, завершённые попытки и отозванные приглашения локальной тестовой организации; не запускайте лишние повторы без причины и учитывайте лимит входа 10 попыток на аккаунт за 15 минут.
6. Для быстрого обновления остановите только контейнерные web/api (`docker compose stop web api`), выполните `make db migrate`, затем запустите `make api` и `make web` отдельными процессами. Vite на 5173 проксирует API на 8080. Браузерные проверки Vite используют E2E_BASE_URL с портом 5173. Не занимайте один API-порт двумя процессами. Для возврата к Compose остановите только свои локальные процессы и выполните make up.

Реализованы сессии, роли, банк вопросов, конструктор и публикация версий тестов, кандидаты, вакансии, назначения оценщиков, приглашения, прохождение, серверный таймер, автосохранение, восстановление и точный подсчёт баллов. HR видит результаты; кандидатский показ управляется опубликованной версией. Readiness требует миграцию 0015 (40 таблиц, 15 миграций). API сам запускает обработчик просроченных попыток сразу при старте и каждые 2 секунды: отдельный процесс или cron не нужны. Все сроки и ответы сохраняются в PostgreSQL. Работают подробные отчёты, снимок категорий для новых попыток, фильтры и экспорт CSV/XLSX с правами и аудитом. Работают администраторский аудит и правила хранения с предпросмотром/подтверждением/запретами. По умолчанию правила выключены; автоматического удаления нет. Реализованы смена пароля, почтовое восстановление с сохранением MFA, TOTP и резервные коды, настройки организации, приглашения сотрудников и комментарии к результатам. Реализован импорт CandidateTester version 1 (single), предварительная проверка и атомарное применение. RLS ещё впереди; индивидуальное удаление и версии согласия реализованы, см. docs/personal-data.md. Не объявляйте полный продукт или production готовыми. При диагностике браузерных ошибок маскируйте base64url-токены перед выводом журнала. Это необязательная проверка для изменений жизненного цикла; оставляет явно помеченные тестовые записи. Не запускайте её на рабочей базе. Перед реальными данными требуется утверждённая политика организации: текущая запись согласия development-passage-v1 предназначена для разработки.

Отчёты: /results и /results/:id в HR-сессии. Подробный отчёт доступен после submitted/expired, оценщику — только по назначенной вакансии. Резервные копии: docs/backups.md. Из корня после активации tools команда make backup создаёт AES-256-GCM архив в .backups (0700/0600), автоматически проверяет восстановление 40 таблиц в новой случайной hr_restorecheck_* базе и удаляет её до публикации готового файла. make backup-verify повторяет проверку; исходная база не заменяется. Локальные копии не заменяют внешнее хранилище. make integration теперь включает cmd/backup и cmd/org-resume и создаёт/удаляет только свои временные базы. Удаление требует make backup-prune DAYS=<период> APPLY=DELETE_OLD_BACKUPS; без APPLY это предпросмотр, последняя копия сохраняется. restore создаёт только свежую hr_recovery_* базу и отключает в ней старые сессии/ссылки; API не переключается. Restore, оставляющий базу, требует --ledger актуальный.hrledger и --confirm CURRENT_ERASURE_LEDGER. make backup-ledger экспортирует минимальный реестр с исходным backup-ключом; хранить отдельно от снимков, обновлять после каждого удаления. Восстановление проверяет линию базы и повторно применяет удаления, а при доступной исходной линии сверяет полный реестр. При потере исходной линии полнота независимого файла — ответственность оператора. Автоматического внешнего хранения/расписания пока нет. Без реестра recovery-база не оставляется.

История этапа безопасности: миграция 0014 добавила индекс технических счётчиков (тогда 36 таблиц / 14 миграций; сейчас 0015 и 40 / 15). happy-dom 21.0.1, 22 Vue-теста, npm audit должен проверять также dev-зависимости. Клиентский IP берётся из X-Forwarded-For только от непосредственного адреса из TRUSTED_PROXY_CIDRS и только с одним IP. Compose доверяет ровно внутреннему Nginx HR_WEB_INTERNAL_IP/32 (по умолчанию 172.30.254.10/32), сеть HR_DOCKER_SUBNET (172.30.254.0/24). Nginx и Vite перезаписывают заголовок. run_backend.py для прямой разработки доверяет loopback Vite; API без настройки не доверяет заголовкам. Не расширяйте доверие на все сети и не считайте внешний HTTPS-прокси настроенным без отдельной конфигурации.

При первом переходе со старой Docker-сети нужно один раз docker compose down (без очистки .local/postgres), затем make up. Это меняет процессы/сеть, сохраняет БД и .env; на уже обновлённой сети повторный down не нужен. Сначала проверьте текущую подсеть docker network inspect hr-testing_default с форматом только IPAM; не выводите полный inspect. Если новая подсеть конфликтует с локальной/VPN, согласованно измените HR_DOCKER_SUBNET и HR_WEB_INTERNAL_IP. На Mac пользователя ничего автоматически не меняется.

Кандидатские GET/POST/PUT и изображения ограничены в БД на IP по минуте: CANDIDATE_IP_LIMIT_PER_MINUTE=600 по умолчанию. Nginx добавляет 20/сек с burst 100 и JSON 429/Retry-After 60. Токены не используются в ключах счётчиков. Лимит общий за NAT; не повторяйте много браузерных прогонов подряд без причины. Раз в минуту worker удаляет до 1000 технических счётчиков старше суток, с повторной проверкой возраста после блокировки; активные окна и персональная политика хранения не затрагиваются. Создание/приглашение/изменение сотрудника повторно проверяет живые права org_admin после ожидания организации. Негативные тесты используют только временные организации и тестовые IP.

Текущие статусы — docs/roadmap.md: пользователь подтвердил локальный Docker и страницу входа на Mac, затем пустую БД. Команда bootstrap предоставлена, успешное создание администратора/ручной вход ещё не подтверждены. Не подменяйте это состоянием облачной тестовой организации. Production-конфигурация подготовлена и проверена в изолированной HTTPS-репетиции без покупки сервисов; следующий этап — эксплуатация и подготовка рабочей почты; технические механизмы индивидуального удаления/версий документов готовы, рабочие тексты утверждает организация; перед реальными данными нужны политика/индивидуальное удаление, реальная почта, внешний backup/мониторинг и пилот. Перед второй компанией — создание организаций/членство/переключение, дополнительная изоляция и квоты. Один сайт и домен могут обслуживать несколько компаний. Новые исправления не отправлять в GitHub без отдельного запроса.


Серверный выпуск: docs/production.md, самостоятельный compose.production.yaml, scripts/production.py. Не объединяйте его с dev compose.yaml и не переносите .env/.local/postgres в production автоматически. Скрипт требует явный абсолютный путь --config к приватному JSON вне checkout и отдельные постоянные данные. init допустим только на новом пустом состоянии: никогда не регенерируйте потерянные ключи существующей БД. Проверка check выполняется офлайн и не доказывает публичное доверие TLS/DNS. Перед настоящим сервером нужны согласованные сервер/домен/сертификат и независимые копии; production-почта пока отключена, локальный make backup новую production-базу не обслуживает; для неё есть отдельный production.py backup, см. docs/operations.md.

Новая команда make admin-docker создаёт первую организацию/администратора штатным bootstrap через operator-образ без Go на хосте. Только на действительно пустой dev-базе; в текущей облачной БД повторно не запускать. Новый администратор/вход на Mac пользователя остаются неподтверждёнными. AUTH_ENCRYPTION_KEY, пароли и авторизацию существующего аккаунта не менять ради проверки.

Для изменений серверной упаковки используйте make production-test и при необходимости make production-smoke после . scripts/cloud_env.sh. Последняя команда собирает runtime/operator/web с предоставленным proxy/CA, создаёт только собственный случайный hr-prod-test-* Compose-проект, отдельную временную БД/ключи/сертификаты, loopback-порты и сеть 172.30.252.0/24. Не запускайте одновременно несколько production-smoke и заранее проверьте отсутствие конфликта подсети. Проверка TLS использует свой тестовый CA и имя hr-testing.test без отключения проверки. Очистка относится только к этой случайной временной базе, не к dev/production данным. Успешный прогон не является внешней публикацией. CI запускает эти проверки, CD ещё не подключён.


Персональные данные (0015): docs/personal-data.md. Полное удаление только org_admin своей организации, свежий предпросмотр 15 минут и фраза УДАЛИТЬ КАНДИДАТА. Удаляется весь кандидатский граф, включая активные попытки и комментарии. Запрет хранения блокирует операцию, в том числе на карточке после очистки контактов. Очистка по сроку остаётся только контактной. Обе операции транзакционно пишут candidate_erasures (UUID/scope/время, без контактов), приложение не меняет/не удаляет реестр. Уже скачанные файлы, старые снимки, WAL, чужие комментарии/общие тексты требуют отдельной процедуры. Не запускайте удаление существующих записей ради проверки среды: только собственные синтетические фикстуры.

Документы организации в /retention: неизменяемые consent_documents; по умолчанию development revision=0 и approved=false. Кандидат видит текущий текст/политику, start отправляет consent_revision. Для новой попытки старая версия отклоняется; повтор ранее подтверждённого start возвращает прежнюю попытку. При COOKIE_SECURE=true новые попытки требуют approved=true. Не утверждайте тестовые тексты в основной организации автоматически. Производственная юридическая политика ещё не предоставлена.

Браузерные тесты поддерживают E2E_CREDENTIALS_FILE — абсолютный путь к приватному JSON локального тестового администратора. По умолчанию прежний .env.admin.json. Для повторных проверок можно выделить синтетического администратора штатным API и отключить после теста; не сбрасывайте основной пароль/MFA и не обнуляйте лимиты входа ради повторов. Теперь доступны 8 e2e, включая удаление на desktop/320. Учётные записи и URL-токены из логов не печатать. Изолированный make integration не разделяет таблицы очередей с работающим dev API или браузером.

IP-лимиты account-security после проверки: ключ account-ip теперь включает family (security/recovery/reset/import), чтобы действия MFA не расходовали recovery-бюджет. Пороги не увеличены; старые ключи очищаются по TTL. Подробности security-hardening.md. Проверка новых сценариев удаления на desktop/320 прошла, мобильный account после исправления лимита перепроверен отдельно. Если браузерный прогон падает, сначала диагностируйте конкретный код ответа; не повторяйте весь набор и не сбрасывайте защитные счётчики без необходимости.

Финальное восстановление/экспорт реестра/переключение выполняются при остановленных изменениях исходной линии в согласованное окно: проверка не покрывает новые удаления после её завершения. API автоматически не переключается.


Эксплуатация: docs/operations.md, scripts/operations.py, infrastructure/production/systemd/. production.py build включает backup-образ PG17; production.py --config /приватный/production.json backup create/verify/erasures использует исходный формат и те же проверки, отдельную production-сеть без Docker socket/Go в инструменте. Никогда не нацеливайте make integration или dev make backup на production. Приватное состояние backup/.backups и backup/.env.backup.key сохраняется внутри HR_STATE_DIR вне checkout; исходный ключ отдельно от зашифрованной реплики. operations configure требует явный отдельный смонтированный каталог и метку установки; --rehearsal разрешён только для синтетических данных и всегда даёт предупреждение check. backup/ledger сериализуются; квитанция обновляется после доставки. Таймеры, внешнее хранилище и отправка уведомлений в текущей облачной среде не устанавливаются/не включаются. Канал ещё не выбран. make production-test теперь запускает все scripts/tests/test_*.py, а production-smoke включает зашифрованные backup/verify/recovery, реплику и остановку API. Повторять только при изменениях/ошибках этих механизмов. Сохраняйте старые копии, не удаляйте ключи/реестры ради проверки и не объявляйте публичную доступность/полную эксплуатационную готовность по локальному прогону.
