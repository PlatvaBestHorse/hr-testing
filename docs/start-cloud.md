# Запуск облачной среды Кадрового тестера

Используйте существующую рабочую копию `/workspace/hr-testing`. Каждая облачная задача уже изолирована; не создавайте Git worktree без запроса пользователя. Основной репозиторий — PlatvaBestHorse/hr-testing, рабочая ветка HR-TESTING. Пользователь разрешил выгрузку текущего проекта в эту ветку. Для последующих изменений выполняйте push только по явному запросу пользователя; используйте обычный push с сохранением удалённой истории. Файлы, зависимости и база сохраняются отдельно от процессов, которые надо запускать после восстановления среды.

1. Из `/workspace/hr-testing` выполните `. scripts/cloud_env.sh`. Активируются Go 1.26.9, доступные кэши, Docker buildx, предоставленный сетевой прокси и проверяемый системный CA-bundle для сборок. Используйте Node.js 24 и Docker Compose. Не выводите значения `.env`, `.env.admin.json` или переменных секретов.
2. Выполните `make up`. Команда сохраняет `.env`, запускает PostgreSQL, применяет миграции владельцем схемы, затем запускает API ограниченной ролью и интерфейс. Не удаляйте `.local/postgres`, не сбрасывайте локальные пользовательские пароли и не меняйте DB-пароли только через `.env`.
3. Локальные запросы к API `/readyz` на порту 8080 и к интерфейсу `/api/v1/status` на 8088 должны вернуть `{"status":"ready"}`. HTML `/login` на 8088 должен содержать заголовок «Кадровый тестер». Наличие порта/контейнера само по себе не доказывает работу приложения. На ошибках смотрите логи только соответствующих сервисов; не выводите docker compose config или полный docker inspect с секретами.
4. В подготовленной базе есть одна организация и тестовый администратор. Его уникальный пароль сохранён в `.env.admin.json` с правами 0600. Bootstrap повторно не нужен. Вход — `/login`; текущие роли/организация/CSRF возвращаются `/api/v1/me`. Браузерные тесты используют этот файл напрямую, не печатая значения. Если файла нет, не выдумывайте пароль существующего аккаунта и не сбрасывайте его. На действительно пустой локальной базе после миграций используйте `make admin` с интерактивным защищённым вводом; `make admin-dev` допустим только в локальном тестовом контуре. В текущем процессе cookie Secure явно отключён для loopback HTTP. Для HTTPS требуется COOKIE_SECURE=true и APP_ORIGINS с точным HTTPS-origin.
5. Проверки разработки: `make check` и `make integration` из корня; `npm run test:e2e` из `frontend` при работающих контейнерах. Для Chromium используется `/usr/bin/chromium`. Обычный Go test без TEST_DATABASE_URL пропускает DB/HTTP-интеграцию, поэтому не подменяет make integration. Интеграция создаёт две временные организации и очищает только их IDs привилегированным test-owner. Не используйте production-базу. Браузерные проверки оставляют помеченные вопросы, тесты, кандидатов, вакансии, завершённые попытки и отозванные приглашения локальной тестовой организации; не запускайте лишние повторы без причины и учитывайте лимит входа 10 попыток на аккаунт за 15 минут.
6. Для быстрого обновления остановите только контейнерные web/api (`docker compose stop web api`), выполните `make db migrate`, затем запустите `make api` и `make web` отдельными процессами. Vite на 5173 проксирует API на 8080. Браузерные проверки Vite используют E2E_BASE_URL с портом 5173. Не занимайте один API-порт двумя процессами. Для возврата к Compose остановите только свои локальные процессы и выполните make up.

Реализованы сессии, роли, банк вопросов, конструктор и публикация версий тестов, кандидаты, вакансии, назначения оценщиков, приглашения, прохождение, серверный таймер, автосохранение, восстановление и точный подсчёт баллов. HR видит результаты; кандидатский показ управляется опубликованной версией. Readiness требует миграцию 0014. API сам запускает обработчик просроченных попыток сразу при старте и каждые 2 секунды: отдельный процесс или cron не нужны. Все сроки и ответы сохраняются в PostgreSQL. Работают подробные отчёты, снимок категорий для новых попыток, фильтры и экспорт CSV/XLSX с правами и аудитом. Работают администраторский аудит и правила хранения с предпросмотром/подтверждением/запретами. По умолчанию правила выключены; автоматического удаления нет. Реализованы смена пароля, почтовое восстановление с сохранением MFA, TOTP и резервные коды, настройки организации, приглашения сотрудников и комментарии к результатам. Реализован импорт CandidateTester version 1 (single), предварительная проверка и атомарное применение. RLS и индивидуальное удаление ещё впереди. Не объявляйте полный продукт или production готовыми. Onboarding UI не поддерживает loopback-предпросмотр; проверяйте локальными запросами и браузерными тестами и сообщайте результаты текстом. Сохранение инструкций в черновик не публикует снимок и не выполняет команды. Поведение в новом восстановленном окружении считается проверенным только после отдельного запуска там.

Секрет приглашения появляется только в ответе выдачи. Не печатайте его и не копируйте в инструкции. Сохраняйте исключение токеновых URL из Nginx access log и отключение URL-содержащего error log для кандидатского API и Referrer-Policy: no-referrer. Кандидатский DTO не должен содержать ключи правильности, explanation, порог, веса или контакты; собственные подтверждённые ответы доступны в активной попытке. score допускается только после завершения при show_candidate_score=true. При диагностике браузерных ошибок маскируйте base64url-токены перед выводом журнала. Проверки прохождения: браузерные сценарии desktop/320 px проходят отключение сети и перезагрузку, модульные — потерянное подтверждение и конфликт вкладок. Дополнительный make runtime-check из корня использует .env.admin.json, перезапускает только локальный Compose API и проверяет восстановление активной попытки, затем завершение фоновым обработчиком через HR/results, без браузера. Это необязательная проверка для изменений жизненного цикла; оставляет явно помеченные тестовые записи. Не запускайте её на рабочей базе. Перед реальными данными требуется утверждённая политика организации: текущая запись согласия development-passage-v1 предназначена для разработки.

Отчёты: /results и /results/:id в HR-сессии. Подробный отчёт доступен после submitted/expired, оценщику — только по назначенной вакансии. Экспорт списка всех страниц ограничен 10 000 строк и применёнными фильтрами; даты начала по МСК. Новые попытки фиксируют category_snapshot, старые явно показывают категории текущего банка. Просмотры и выгрузки пишутся в аудит. Браузерные тесты сохраняют CSV/XLSX в игнорируемые test-results; их можно проверить openpyxl в текущем runner. Серверные проверки CSV/ZIP/XML не заменяют проверку содержимого книги независимым читателем. Не запускайте runtime-check одновременно с Playwright: он временно останавливает API.

Аудит/хранение: /audit и /retention доступны только org_admin. Не запускайте очистку существующих данных только для проверки среды. Проверки make integration выполняют удаление лишь в изолированных временных организациях; browser e2e устанавливает и снимает запрет своей тестовой карточки, не включает политику основной организации. Применение требует свежий предпросмотр, актуальную сессию/версию правил и фразу подтверждения; повтор ID возвращает прежний результат. БД app-role читает/добавляет аудит, но не обновляет/удаляет напрямую: prune_audit_events выполняет узкую проверенную очистку. Не возвращайте UPDATE/DELETE права ради теста. После обновления готовы 22 Vue-теста и дополнительные DB/HTTP сценарии управления данными.

Резервные копии: docs/backups.md. Из корня после активации tools команда make backup создаёт AES-256-GCM архив в .backups (0700/0600), автоматически проверяет восстановление 36 таблиц в новой случайной hr_restorecheck_* базе и удаляет её до публикации готового файла. make backup-verify повторяет проверку; исходная база не заменяется. Сохраняйте .env.backup.key (0600), не печатайте ключ, не включайте его или .backups в Git/ZIP исходников. При отсутствии ключа и наличии копий не генерируйте новый. Локальные копии не заменяют внешнее хранилище. make integration теперь включает cmd/backup и cmd/org-resume и создаёт/удаляет только свои временные базы. Никогда не используйте ConnConfig.ConnString() после изменения Database для подключения: pgx сохраняет исходную строку; подключайте изменённый ConnConfig напрямую. Не запускайте очистку копий для проверки запуска. Удаление требует make backup-prune DAYS=<период> APPLY=DELETE_OLD_BACKUPS; без APPLY это предпросмотр, последняя копия сохраняется. restore создаёт только свежую hr_recovery_* базу и отключает в ней старые сессии/ссылки; API не переключается. До запуска восстановленной базы требуется сверка удалений после снимка; независимый реестр и внешнее расписание ещё не реализованы.

Настройки /settings: закрытие организации требует явную фразу и отзывает сессии. Не приостанавливайте основную организацию для проверки. Безопасность после аудита: миграция 0014 добавляет индекс технических счётчиков; 36 таблиц, 14 миграций. happy-dom 21.0.1, 22 Vue-теста, npm audit должен проверять также dev-зависимости. Клиентский IP берётся из X-Forwarded-For только от непосредственного адреса из TRUSTED_PROXY_CIDRS и только с одним IP. Compose доверяет ровно внутреннему Nginx HR_WEB_INTERNAL_IP/32 (по умолчанию 172.30.254.10/32), сеть HR_DOCKER_SUBNET (172.30.254.0/24). Nginx и Vite перезаписывают заголовок. run_backend.py для прямой разработки доверяет loopback Vite; API без настройки не доверяет заголовкам. Не расширяйте доверие на все сети и не считайте внешний HTTPS-прокси настроенным без отдельной конфигурации.

При первом переходе со старой Docker-сети нужно один раз docker compose down (без очистки .local/postgres), затем make up. Это меняет процессы/сеть, сохраняет БД и .env; на уже обновлённой сети повторный down не нужен. Сначала проверьте текущую подсеть docker network inspect hr-testing_default с форматом только IPAM; не выводите полный inspect. Если новая подсеть конфликтует с локальной/VPN, согласованно измените HR_DOCKER_SUBNET и HR_WEB_INTERNAL_IP. На Mac пользователя ничего автоматически не меняется.

Кандидатские GET/POST/PUT и изображения ограничены в БД на IP по минуте: CANDIDATE_IP_LIMIT_PER_MINUTE=600 по умолчанию. Nginx добавляет 20/сек с burst 100 и JSON 429/Retry-After 60. Токены не используются в ключах счётчиков. Лимит общий за NAT; не повторяйте много браузерных прогонов подряд без причины. Раз в минуту worker удаляет до 1000 технических счётчиков старше суток, с повторной проверкой возраста после блокировки; активные окна и персональная политика хранения не затрагиваются. Создание/приглашение/изменение сотрудника повторно проверяет живые права org_admin после ожидания организации. Негативные тесты используют только временные организации и тестовые IP.
