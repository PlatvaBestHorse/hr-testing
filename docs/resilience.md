# Нагрузочная и аварийная репетиция

Подготовлена команда `make resilience-check`. Она сама создаёт новую синтетическую HTTPS-установку через существующую production-репетицию, выполняет проверки и удаляет только собственные контейнеры/БД. Адрес рабочей установки ей передать нельзя. Dev-база, учётная запись основного администратора, реальные ключи/копии и Docker Desktop пользователя не используются.

| Компонент | Назначение | Нужен сейчас | Дальнейшее действие |
|---|---|---|---|
| `scripts/check_resilience.py` | Нагрузка и аварийные проверки через реальный Nginx/Go/PostgreSQL | Да, для изменений перед пилотом | Запускать при изменении прохождения, серверной упаковки или восстановления |
| Существующая `check_production.py` | Отдельный контур, синтетический bootstrap, доверенный тестовый TLS, backup/recovery и очистка | Используется повторно | Поддерживать вместе с production-манифестом; архитектура приложения не меняется |
| Приватный JSON отчёта | Числа, статусы и результат последнего запуска без токенов/ответов/контактов | Да, для проверки результата | Смотреть `passed`, время, исходный commit и `source_dirty`; старый отчёт не доказывает новый запуск |
| GitHub Actions | Повтор проверки после push и сохранение только отчёта | Уже подключено к существующему CI | Проверять результат конкретного commit; публикации сайта/CD по-прежнему нет |
| Профиль будущего сервера | Проверка реального оборудования, сети и типичного банка | После выбора инфраструктуры | Отдельно проверить 50+ вопросов, изображения, большой объём истории и длительную нагрузку |

## Запуск

В корне проекта нужны Docker Compose v2, Python 3.11 или новее (существующая проверка реплики использует `hashlib.file_digest`), OpenSSL и доступные исходные образы. Go на хосте для этой команды не нужен: бинарники собираются в Docker. В управляемой облачной среде сначала `. scripts/cloud_env.sh`; предоставленные proxy/CA и проверка TLS сохраняются.

```bash
make production-test
make resilience-check
```

Отчёт: `.validation/resilience.json` (0600, каталог исключён из Git). Не меняйте права PG-каталога для записи отчётов. Дополнительные параметры:

```bash
python3 scripts/check_resilience.py --report /приватный/каталог/report.json --p95-ms 3000
```

Число кандидатов фиксировано: группы 5, 10 и 20, всего 35 отдельных прохождений, плюс две попытки для конкурентных/аварийных сценариев. Порог p95 — условие этой репетиции, его исходное значение 3000 мс не является SLA продукта. Ошибка проверки, превышение порога или неудачная очистка дают ненулевой код и `passed=false`; значение `exercise_passed` относится только к дополнительным сценариям до финальных backup/recovery и очистки. JSON записывается и при ошибке, если каталог отчёта доступен.

Контур использует случайный проект `hr-prod-test-*`, временные файлы под `/tmp/hr-production-smoke-*`, loopback-порты, имя `hr-testing.test` и сеть `172.30.252.0/24`. Не запускайте одновременно с другой production-репетицией: эта сеть общая по настройке. Сначала проверьте свободное место, поскольку репетиция включает сборки и временное восстановление копии. При ошибке очистки сохранённый временный каталог требует осмотра оператора; нельзя удалять чужие проекты или реальные PG-данные.

## Что проверяется

Каждый тест содержит три вопроса: один ответ (2.50), вербальная оценка (1.25) и несколько ответов (0.25). Участники отвечают либо на всё верно, либо ошибаются в первом вопросе: ожидаются 100.00% и 37.50%. В одном опубликованном тесте итог виден кандидату, в другом скрыт. Порог 62.50%. Порядок вопросов/вариантов перемешивается. Утверждаются только явно синтетические тексты в новой временной организации; документы существующих организаций не меняются.

В каждой группе одновременно выполняются HTTPS-вызовы открытия ссылки, старта, повторного старта, трёх сохранений, повторного сохранения, восстановления, завершения, повторного завершения и чтения итога. Между группами параллельных запросов выдерживается минимум 1.25 секунды; обычные лимиты Nginx и кандидатского API не отключаются/не повышаются, IP не подменяется. Это 385 штатных кандидатских запросов. Отчёты HR дополнительно сверяются с сохранёнными ответами. Рекурсивно проверяется отсутствие правильных ответов/пояснений и других закрытых полей в кандидатском JSON.

Аварийные сценарии:

1. Десять одинаковых параллельных стартов возвращают одну попытку; десять одинаковых сохранений — одну квитанцию/ревизию.
2. Два разных сохранения с одной исходной ревизией дают один успех и один HTTP 409; подтверждённый ответ совпадает с победившим запросом.
3. Клиент намеренно отбрасывает подтверждение успешной записи. API останавливается с нулевым временем ожидания (`stop -t 0`); запись во время недоступности не подтверждается. После запуска возвращаются прежние попытка/срок/ответ, повтор уже принятого request_id не создаёт новую ревизию, повтор неподтверждённого запроса сохраняется один раз.
4. Так же принудительно останавливается PostgreSQL, API остаётся запущенным. `/api/v1/status` возвращает 503, внутренний API `/healthz` и статический интерфейс доступны. Запись при недоступной БД получает ошибку. После запуска БД сохранённые ответы, порядок и срок совпадают; повтор неподтверждённой записи и итоговый подсчёт успешны. Прежняя HR-сессия действует.
5. Отдельная попытка имеет срок 20 секунд. Пока API остановлен, срок проходит; после запуска результат проверяется **через HR-отчёт**, без кандидатского обращения, способного само завершить попытку. Фоновый обработчик ставит `expired`, фиксирует исходный deadline и 62.50%. Новая запись отвергается, повтор старой подтверждённой записи возвращает прежнюю квитанцию.
6. В захваченных в памяти логах Nginx/API отсутствуют выданные секреты приглашений и секретные значения конфигурации. Логи/URL/правильные ответы в JSON отчёта не переносятся.

Репетиция завершается существующими production backup/verify/recovery, проверкой реплики и остановленного API. Основная тестовая сессия сохраняется при восстановлении в отдельную БД. Это уже не включается в метрики штатной кандидатской нагрузки.

Задержка измеряется клиентом с установлением нового проверяемого TLS-соединения и чтением ответа; ожидание между фазами в неё не включается. Намеренные ошибки аварийных сценариев отдельно учитываются в отчёте и не смешиваются со штатным p95. Числа относятся к малой синтетической базе и этой облачной машине с общими ресурсами. Они не устанавливают максимальное число пользователей, производительность будущего сервера или допустимость реальной нагрузки.

Python-проверки: 22 теста, включая защиту от выбора dev/production для аварий, утечку закрытых полей, p95 на малой выборке, сокрытие bearer/текста ответа в ошибках и невозможность оставить успешный отчёт при неудачном запуске. Исходный защищённый JSON сохранён локально; в Git входят сценарии и этот обезличенный отчёт. Новый запуск GitHub Actions после push надо оценивать отдельно. CI сохраняет только `.validation/resilience.json` как артефакт на 14 дней; сырые логи, `.env`, ключи и БД туда не добавляются.

## Что ещё остаётся

Эта проверка не моделирует повреждение/потерю диска и всего сервера, WAN/VPN, внезапное отключение хоста, длительные 50-вопросные прохождения, массовые изображения/экспорты, большой объём истории или отказ независимого хранилища. Резервирование здесь проверяется синтетической файловой репликой на той же машине. Нужны выбранный сервер и требования к нагрузке, внешняя реплика/проверка, фактическая доставка уведомлений и согласованные RPO/RTO. Дальше — ручная приёмка одной компании на синтетических данных и более длительный профиль на целевой инфраструктуре. Рабочая почта и утверждённые документы подключаются после получения соответствующих настроек/текстов.
