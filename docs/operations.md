# Резервирование и контроль состояния

Это продолжение существующей Docker/PostgreSQL-схемы. Платные сервисы не подключаются. Команды ниже относятся **только к явно выбранному production JSON**, не к `.env` разработки или Docker Desktop пользователя. Сервер и внешнее хранилище ещё не выбраны; таймеры в облачной среде разработки не устанавливаются.

| Компонент | Назначение | Когда нужен | Дальнейшее действие |
|---|---|---|---|
| Образ `backup` с PostgreSQL 17 client | Тот же зашифрованный `.hrbak`, проверка настоящим восстановлением и права ограниченной роли | До рабочих данных | Собрать вместе с выпуском, выполнить первую копию |
| Отдельный каталог реплики | Копирование только `.hrbak`/`.hrledger`, контроль SHA256, атомарная публикация, без перезаписи повреждённого файла | До рабочих данных | Выбрать независимое защищённое хранилище и смонтировать его на сервере |
| Приватные ключи и конфигурация | Расшифровка копий, MFA и восстановление подключения | Сейчас при создании установки | Вручную сохранить независимые защищённые копии; не складывать ключ архива рядом с его репликой |
| `operations.py` и systemd | Ежедневный backup, реестр каждые 5 минут, контроль каждые 2 минуты | На выбранном Linux-сервере | Примерить пути/права, проверить вручную, затем включить таймеры |
| Локальный alert hook (необязательный) | Передать оператору техническое событие через выбранный им канал | До пилота | Подключить собственный исполняемый файл; проверить доставку и восстановление |
| Внешняя проверка сайта | Обнаружить проблемы DNS, внешней сети, публичного TLS и самого сервера | После выбора домена/сервера | Выбрать отдельную от сервера проверку; текущая локальная команда её не заменяет |

## Production-копия без Go на хосте

Сначала выполните подготовку из [production.md](production.md). Соберите новый выпуск: `python3 scripts/production.py --config /etc/hr-testing/production.json build`. Пароли не передаются в аргументах команды. Новый инструмент работает внутри сети Compose с ролью владельца миграций; он не получает Docker socket, ключ авторизации, порт наружу или доступ к PG-каталогу. API продолжает работать с ограниченной ролью `hr_app`.

```bash
python3 scripts/production.py --config /etc/hr-testing/production.json backup create
python3 scripts/production.py --config /etc/hr-testing/production.json backup verify
python3 scripts/production.py --config /etc/hr-testing/production.json backup erasures
python3 scripts/production.py --config /etc/hr-testing/production.json backup list
```

Данные: `<HR_STATE_DIR>/backup/.backups/` (0700, файлы 0600). Исходный ключ: `<HR_STATE_DIR>/backup/.env.backup.key` (0600). Генерируется один раз при `create`; при наличии архивов/реестров потерянный ключ не заменяется. Сохраняйте независимо также исходный production JSON с `AUTH_ENCRYPTION_KEY`, `<HR_STATE_DIR>/identity.json`, исходники/точный выпуск и внешние файлы, если появятся. Автоматическая реплика намеренно копирует только зашифрованные данные, без ключей, JSON конфигурации и сырых SQL-дампов.

`create` публикует архив только после реального восстановления во временную БД, проверки содержимого всех таблиц, миграций, прав и неизменяемых версий. На диске должны одновременно помещаться основная БД, её временное восстановление и архив. Есть ограничение операции 30 минут; для большой БД нужны отдельная оценка времени и места. Совместимость схемы требует текущих 15 миграций; старые архивы сохраняйте вместе с соответствующим выпуском.

## Реплика и расписание

Пример путей: исходники `/opt/hr-testing`, приватная конфигурация `/etc/hr-testing`, состояние `/var/lib/hr-testing`, **уже смонтированное независимое** хранилище `/srv/hr-testing-replica`. Каталоги конфигурации/состояния/реплики должны принадлежать операторскому пользователю и иметь 0700. Он должен иметь доступ к Docker и чтению TLS-ключа. Доступ к Docker предоставляется только доверенному оператору сервера. Сначала подготовьте защищённое монтирование штатными средствами выбранного хранилища; инструмент не подключает SSH/S3 и не хранит их реквизиты.

```bash
python3 scripts/operations.py --config /etc/hr-testing/production.json --ops /etc/hr-testing/operations.json configure --replica-dir /srv/hr-testing-replica
python3 scripts/operations.py --config /etc/hr-testing/production.json --ops /etc/hr-testing/operations.json backup
python3 scripts/operations.py --config /etc/hr-testing/production.json --ops /etc/hr-testing/operations.json check
```

При настройке создаётся приватная метка установки в реплике. Проверяются метка, ключевая идентичность и отличающийся от основного состояния filesystem device. При пропаже монтирования программа завершается ошибкой, не создаёт незаметно локальный запасной каталог. Отличающийся device сам по себе не доказывает удалённость, надёжность и изоляцию доступа: второй локальный диск не защищает от потери всего сервера. Для синтетической репетиции есть явный `configure --rehearsal`; проверка состояния всегда отмечает такую реплику как недостаточную для production.

Копирование сверяет размер/SHA256, синхронизирует запись и публикует файл без замены существующего. Хранилище должно поддерживать POSIX-права, fsync и hard links; обычная объектная корзина без подходящего файлового слоя не подходит. На неподдерживаемой файловой системе операция завершится ошибкой. Доставка реестра не зависит от ежедневного архива: команда `ledger` экспортирует свежий реестр и копирует его отдельно. Квитанция успеха обновляется только после успешной доставки всех файлов текущего запуска. Одновременные `backup`/`ledger` блокируются локальным lock; проигравший запуск возвращает ошибку и повторяется следующим таймером. Во время долгого backup реестр может отставать — это обнаружит контроль свежести.

Готовые Linux systemd-файлы — `infrastructure/production/systemd/`. Они рассчитаны на перечисленные выше пути и пользователя `hr-testing`; сначала проверьте их на своём сервере. Docker daemon выбирается явно через локальный socket. Подготовьте также приватный каталог `/etc/hr-testing/docker` (0700, владелец оператор): это DOCKER_CONFIG для unit, домашний каталог закрыт ProtectHome. Если для уже собранных образов понадобятся настройки registry/proxy, храните их там защищённо и проверьте запуск от пользователя unit. Если пути отличаются, измените `WorkingDirectory`, `ExecStart`, `ReadWritePaths`; для хранилища добавьте зависимость от его mount-unit. Не копируйте эти настройки на macOS: там расписание требует отдельной настройки launchd; ручные Docker-команды работают.

После ручного успешного прогона на выбранном сервере:

```bash
sudo install -m 0644 infrastructure/production/systemd/hr-testing-ops@.service /etc/systemd/system/
sudo install -m 0644 infrastructure/production/systemd/hr-testing-backup.timer /etc/systemd/system/
sudo install -m 0644 infrastructure/production/systemd/hr-testing-ledger.timer /etc/systemd/system/
sudo install -m 0644 infrastructure/production/systemd/hr-testing-check.timer /etc/systemd/system/
sudo systemd-analyze verify /etc/systemd/system/hr-testing-ops@.service /etc/systemd/system/hr-testing-*.timer
sudo systemctl daemon-reload
sudo systemctl enable --now hr-testing-backup.timer hr-testing-ledger.timer hr-testing-check.timer
systemctl list-timers 'hr-testing-*'
journalctl -u 'hr-testing-ops@*' --since today
```

Ежедневная копия в 02:00 UTC (05:00 Москвы), реестр раз в 5 минут, контроль раз в 2 минуты. `Persistent=true` догоняет пропущенный календарный запуск после включения. Это расписание не является SLA: оператор согласует допустимую потерю данных (RPO), время восстановления (RTO), режим обслуживания и фактическое время доставки. Полные копии без WAL/PITR не позволяют восстановить произвольную секунду. Между удалением и экспортом реестра существует окно потери последних записей при аварии; для строгого требования «ни одного возвращённого удаления» нужен дополнительный независимый учёт обращений/подтверждённая доставка. После важного удаления запускайте `ledger` вручную и проверяйте результат.

Старые копии/реестры автоматически не удаляются. Есть прежний ручной `backup prune --days N` с предпросмотром и отдельной фразой; реплики и журналы он не удаляет. Сроки/процедуру очистки независимого хранилища и ключей утверждает организация. Контроль свободного места не заменяет этот регламент.

## Контроль и уведомления

`check` проверяет здоровые контейнеры `db/api/web`, настоящий API `/readyz` с проверкой схемы/БД, место на состоянии и реплике (минимум 2 ГиБ и 10%), офлайн соответствие TLS-пары/имени и остаток не менее 7 дней, квитанцию доставки и SHA256 **последнего** архива/реестра в обеих копиях. Сигнал просрочки: архив старше 26 часов, реестр старше 15 минут. Проверка хешей читает целиком последний архив дважды; для больших объёмов нужно пересмотреть частоту и бюджет I/O. Устаревшие архивы при каждом опросе не перечитываются. Нет автоматического рестарта, переключения БД, продления TLS или очистки данных.

События JSON содержат только проект, время и технические коды. Код возврата 0 — проверка успешна, 1 — есть проблема. Квитанции/состояние 0600 сохраняются в `HR_STATE_DIR`; ошибки команд не включают SQL, пароли, контакты или токены. Это проверки доступности, не полноценные метрики нагрузки/HTTP-ошибок. Внешняя доступность, потеря самого сервера/таймера и доверие публичной цепочки требуют отдельной проверки с другой машины.

По умолчанию события остаются в терминале/journald. Реальная отправка кому-либо **не включена**. Для выбранного оператором канала при `configure` укажите `--alert-program /etc/hr-testing/alert-hook`: абсолютный путь вне исходников, приватный исполняемый файл 0700. При необходимости изменить уже созданную конфигурацию отредактируйте только поле `alert_program` в приватном JSON, сохранив 0600 и остальные поля. Программа запускается без shell, получает JSON на stdin, должна завершиться за 10 секунд с кодом 0 при принятом событии; stdout/stderr отбрасываются. Секреты канала хранятся отдельно, не в исходниках и не в аргументах. Передаются изменение состояния, восстановление и повтор непрерывной ошибки не чаще часа. Ошибка hook видна как `notification_failed` и повторяется; при повреждённой основной конфигурации/самого hook остаются stderr/journal, поэтому независимая проверка необходима.

## Восстановление и обновление

1. Зафиксируйте инцидент, остановите изменения API/почты/кандидатов в согласованное окно. Сохраните доступное исходное состояние; не делайте `down -v` и не удаляйте PG-каталог.
2. Получите нужный архив, **последний подтверждённый реестр**, исходный ключ архива и AUTH-ключ из независимых источников. Если локальные копии потеряны, подготовьте отдельный изолированный recovery Compose-контур с тем же выпуском/ключом. Новые ключи не расшифруют старые данные.
3. Верните выбранные файлы 0600 в `<HR_STATE_DIR>/backup/.backups/`, исходный ключ — в `<HR_STATE_DIR>/backup/.env.backup.key`. Для примера замените имена ниже точными именами файлов:

```bash
python3 scripts/production.py --config /etc/hr-testing/production.json backup verify --file /backupstate/.backups/hr-ИМЯ.hrbak
python3 scripts/production.py --config /etc/hr-testing/production.json backup restore --file /backupstate/.backups/hr-ИМЯ.hrbak --ledger /backupstate/.backups/erasure-ИМЯ.hrledger --target hr_recovery_incident --confirm CURRENT_ERASURE_LEDGER
```

4. Проверяется свежая несуществующая recovery-БД, совпадение содержимого и прав, затем повторяются удаления. Старые сессии/ссылки/почта отзываются, действующий MFA требует исходного AUTH-ключа. Рабочая БД не заменяется, API автоматически не переключается. Полноту реестра, исправления контактов и запреты после снимка проверяет оператор. Дополнительные ограничения — [backups.md](backups.md) и [personal-data.md](personal-data.md).
5. Проверьте восстановленный контур изолированно; только затем согласуйте точное переключение подключения и новую выдачу ссылок. Не подменяйте `POSTGRES_DB` у существующего каталога, не применяйте старую схему к новым исходникам автоматически.
6. Перед обновлением сделайте проверенную копию+реестр, сохраните tag/конфигурацию предыдущего выпуска. При неудачном обновлении оставьте доступ закрытым, изучите совместимость миграций: возврат старого образа не откатывает схему. При несовместимости используйте отдельное восстановление, сверку удалений и операторское переключение. Автоматического отката данных нет.

Проверки разработчика: `make production-test`; `make production-smoke` создаёт только свою синтетическую установку/сертификаты/реплику, делает production-backup, verify и recovery, подтверждает сохранение рабочей сессии и обнаружение остановленного API, затем удаляет только собственную временную среду. Успешный прогон не доказывает работу будущего внешнего хранилища/таймеров/канала уведомлений.

Расширенный `make resilience-check` использует тот же контур, добавляя группы кандидатов и аварии API/БД. Он уже включает все проверки `production-smoke`; два полных запуска подряд для одной и той же версии не нужны. Профиль/метрики/ограничения — [resilience.md](resilience.md). При сохранении отчётов в CI выбирается только обезличенный JSON, не ключи/копии/сырые логи.
