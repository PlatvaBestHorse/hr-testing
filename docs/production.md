# Серверная конфигурация и выпуск

Изолированная нагрузочная и аварийная проверка текущей конфигурации: [resilience.md](resilience.md), `make resilience-check`. Она включает прежнюю HTTPS/backup-репетицию и не запускает команды на уже существующей production-базе.

Подготовлен отдельный Docker Compose-контур для одного сервера: PostgreSQL 17, Go API и Nginx с Vue и TLS. Он соответствует текущему стеку и не требует переписывать серверную часть под Vercel. Сервер, домен, сертификат и внешние сервисы пока не подключены. Эта инструкция не означает готовность к работе с реальными персональными данными.

## Состав

| Компонент | Назначение | Нужен сейчас | Дальнейшее действие |
|---|---|---|---|
| Docker Engine и Compose v2 на Linux | Запуск существующих API, фонового обработчика и интерфейса | Для репетиции — локальный Docker; для публикации нужен сервер | Выбрать сервер и защищённый доступ; платные сервисы автоматически не подключаются |
| PostgreSQL 17 | Постоянные данные, сессии, результаты, изображения | Да, уже включён | Каталог вне checkout, отдельные роли приложения/миграций, внешние копии перед реальными данными |
| Nginx + TLS | HTTPS, статические файлы и прокси API | Да для публичного сервера | Настроить DNS, доверенный fullchain и автоматическое продление сертификата |
| Образ оператора | Первичная организация/администратор, пароль, возобновление организации | Да | Запускать штатные CLI без Go на сервере; пароль вводить скрыто |
| SMTP | Восстановление пароля и приглашения сотрудников | Позже: сервис ещё не выбран | В серверной конфигурации почта отключена; отдельный этап защищённого SMTP и проверки доставки |
| Зашифрованные копии и мониторинг | Восстановление после потери сервера, контроль сбоев/диска | Обязательны перед реальными данными | Production-команда `backup`, реплика и таймеры подготовлены; подключение внешнего хранилища/уведомлений — [operations.md](operations.md). `make backup` остаётся dev-командой |
| GitHub Actions CI | Проверка исходников и HTTPS-репетиция | Уже есть | CD, публикация образов и доступ на сервер — отдельный этап |

`compose.production.yaml` используется самостоятельно, без `compose.yaml`. Имя проекта по умолчанию `hr-testing-prod`; `hr-testing` зарезервировано за разработкой. Только Nginx публикует 80/443. PostgreSQL и API доступны во внутренней Docker-сети. Межконтейнерное соединение БД без TLS допустимо здесь в пределах одного сервера; подключение к внешней БД потребует отдельной настройки TLS. Доступ root/Docker к серверу означает доступ к данным и секретам.

API работает без root, с read-only файловой системой и без Linux capabilities. Nginx читает закрытый TLS-ключ своим master-процессом. Приложение доверяет клиентский IP только фиксированному адресу Nginx /32; тот перезаписывает заголовки. Внешний CDN/прокси перед Nginx этой схемой не настроен. При конфликте подсети с VPN меняйте подсеть и адрес Nginx согласованно до запуска.

## Подготовка из GitHub

1. Проверить ветку `HR-TESTING` и успешные CI-проверки. Для выпуска выбрать конкретный коммит. Доступ к GitHub использовать штатный; не вставлять токены в команды/URL.
2. На выбранном Linux-сервере установить Docker Engine с Compose v2, Python 3 и OpenSSL 3 (поддержка x509 -checkhost/-checkend). Получить исходники через `git clone`, открыть папку проекта и переключиться на выбранный коммит. Go и Node на сервере не нужны: сборка внутри Docker.
3. Создать отдельный закрытый каталог конфигурации. Пример ниже предполагает, что `/srv/hr-testing` принадлежит оператору и имеет права 0700. Исходники должны находиться в другом каталоге. Открыть во внешнем firewall только необходимые порты: 80/443 и ограниченный административный SSH. Порты 5432/8080 не открывать.
4. Направить DNS выбранного домена на сервер. Получить публичный сертификат с полным цепочечным файлом и приватным ключом через выбранный ACME-клиент/провайдера. Автоматическая выдача и продление в проект пока не включены. Ключ должен быть 0600 или 0400. Сертификаты и конфигурация хранятся вне Git.
5. Только на **новом пустом** контуре создать конфигурацию. `test.example.org` ниже заменить своим доменом; пути TLS — на действительные:

```bash
release=$(git rev-parse --short=12 HEAD)
python3 scripts/production.py --config /srv/hr-testing/config.json init \
  --state /srv/hr-testing/data \
  --host test.example.org \
  --cert /srv/hr-testing/tls/fullchain.pem \
  --key /srv/hr-testing/tls/privkey.pem \
  --release "$release"
python3 scripts/production.py --config /srv/hr-testing/config.json check
python3 scripts/production.py --config /srv/hr-testing/config.json build
python3 scripts/production.py --config /srv/hr-testing/config.json up
```

`init` генерирует уникальные DB-пароли и AUTH_ENCRYPTION_KEY, не выводит их и не перезаписывает существующий каталог данных. `config.json` — приватный JSON, его нельзя выполнять через `source`. Файл `data/identity.json` хранит только отпечаток ключей и предотвращает случайный запуск со сменёнными ключами. Потерянную конфигурацию нужно восстановить из защищённой копии; повторный `init` не восстанавливает доступ к существующей БД. Не меняйте DB-пароль только в файле: пароль роли PostgreSQL от этого не меняется.

`check` проверяет права, согласованность конфигурации, соответствие ключа сертификату, имя домена и срок не менее суток. Проверка офлайн не подтверждает DNS, публичное доверие цепочки, доступ снаружи или настройку продления. Для публичного запуска отдельно проверить браузером доверенный HTTPS и сетевую доступность.

6. Создать первую организацию и администратора штатным bootstrap:

```bash
python3 scripts/production.py --config /srv/hr-testing/config.json admin
```

Введите рабочую почту администратора и уникальный пароль минимум 12 символов в скрытом запросе. Пароль не передаётся аргументом или через shell history. Bootstrap создаёт организацию и `org_admin` одной транзакцией; повтор на непустой БД запрещён. Отдельный сайт на каждую компанию не нужен; создание второй организации — будущий этап SaaS.

7. Открыть HTTPS-домен, проверить вход, включить MFA, сохранить резервные коды в защищённом месте. В разделе хранения задать утверждённые организацией согласие/политику: при HTTPS новые прохождения без утверждения блокируются. Механизм индивидуального удаления подготовлен, но до реальных данных нужны рабочая политика и регламент обработки внешних копий, почта, независимые резервные копии/реестр удалений, мониторинг и пилот. См. personal-data.md.

## Обновление и обслуживание

Перед обновлением — проверенная независимая копия БД и **исходного AUTH_ENCRYPTION_KEY**, согласованное окно обслуживания. Обычный `make backup` сюда не подключён. Миграции идут вперёд; автоматического отката схемы нет. Пока не выполнен эксплуатационный этап, использовать только синтетические данные.

```bash
git fetch origin
git checkout <проверенный-коммит>
python3 scripts/production.py --config /srv/hr-testing/config.json set-release --release <метка-коммита>
python3 scripts/production.py --config /srv/hr-testing/config.json build
python3 scripts/production.py --config /srv/hr-testing/config.json up
python3 scripts/production.py --config /srv/hr-testing/config.json status
```

Для каждого выпуска используйте новую метку коммита; не пересобирайте разные версии под старой меткой. `up` ждёт PostgreSQL, применяет миграции владельцем схемы, пересоздаёт API и затем Nginx с проверкой healthcheck. Это обновление с коротким перерывом, без гарантии нулевого простоя. БД, ключи и данные вне checkout сохраняются. При ошибке миграции до пересоздания API команда прекращается. Ошибка запуска новой версии не вызывает автоматического возврата старой: проверить совместимость схемы и действовать по будущему регламенту восстановления.

После замены TLS-файлов выполните `check`, затем `reload-tls`: Nginx пересоздаётся, чтобы перечитать и атомарно заменённые bind-mounted файлы. Требуется отдельное наблюдение за сроком сертификата.

Команды `set-password` и `resume` используют прежние механизмы авторизации: первая меняет пароль и отзывает сессии, сохраняя активный MFA; вторая спрашивает точный UUID приостановленной/архивной организации, использует owner и пишет аудит. Обычный bootstrap и смена пароля используют `hr_app`. Никогда не выдавайте owner-реквизиты работающему API.

`down` останавливает только этот Compose-проект и сохраняет данные. Не удаляйте каталог `data`, ключи и существующие копии. Не выводите `config.json`, полный `docker inspect` или раскрытый `docker compose config`: они содержат секреты. Логи API не содержат пароли/токены, но служебные логи и IP тоже требуют ограниченного доступа. Для каждого контейнера включена ротация Docker-логов: до трёх файлов по 10 МиБ. Внешние журналы, мониторинг диска и уведомления относятся к эксплуатационному этапу.

## Локальная проверка серверной схемы

```bash
make production-test
make production-smoke
```

В облачной среде сначала `. scripts/cloud_env.sh`: отдельный `compose.production.cloud.yaml` добавляет предоставленные proxy/CA только при сборке. На обычном Mac/Linux это дополнение не требуется.

Репетиция создаёт собственные временные конфигурацию, CA, сертификат для зарезервированного `hr-testing.test`, организацию и PostgreSQL. Порты слушают только loopback; сертификат проверяется по тестовому CA и имени, TLS-проверка не отключается. Проверяются HTTPS, cookie Secure/HttpOnly, CSRF, отсутствие публичных API/DB-портов и сохранность сессии/вопроса после полной остановки/запуска с повторными миграциями. Очищаются только случайный тестовый Compose-проект и его временные файлы; текущая `.local/postgres` не используется. Это не публикация сайта и не проверка публичного сертификата.

## Дальнейшее автоматическое развёртывание

Сейчас GitHub Actions выполняет тесты, аудит npm и HTTPS-репетицию. Для CD после выбора сервера: публиковать образы конкретного коммита, настроить защищённую среду GitHub с ограниченным доступом, до миграций проверять внешнюю копию, после запуска проверять HTTPS/вход и уведомлять о сбое. Пароли, AUTH_ENCRYPTION_KEY и TLS-ключ на сервере не заменяются исходниками из Git. Реальный сервер, registry-публикация и платные услуги в этом этапе не подключаются.
