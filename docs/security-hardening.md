# Исправления безопасности перед публикацией

Этап после аудита коммита 553803d. Существующие роли, cookie-сессии, Argon2id, TOTP и организация из сессии сохраняются. Production и платные сервисы не подключались. Это технический этап; политика персональных данных и публичное HTTPS-размещение остаются отдельной работой.

## Адрес клиента и доверенный прокси

API использует один общий метод clientIP для входа, безопасности аккаунта, восстановления, импорта и кандидатских запросов. По умолчанию forwarding-заголовки не доверены. TRUSTED_PROXY_CIDRS задаёт явные CIDR доверенных непосредственных прокси; * и /0 отвергаются. Допускается только один корректный адрес в X-Forwarded-For, без списка, порта, zone ID или нескольких заголовков. IPv4-mapped адреса приводятся к IPv4. Недоверенные/неверные заголовки игнорируются. X-Real-IP и Forwarded не используются.

Nginx перезаписывает X-Forwarded-For своим remote_addr и удаляет альтернативные заголовки; Vite делает то же самое. Для прямой разработки через run_backend.py доверены только loopback-адреса Vite. Сетевые обёртки не должны передавать пользовательский заголовок без перезаписи.

В Compose Nginx имеет фиксированный внутренний IPv4, по умолчанию 172.30.254.10, а API доверяет ровно этому /32. Подсеть проекта — 172.30.254.0/24. Это локальные значения, не адреса интернет-сервиса. При конфликте с Docker/VPN измените вместе HR_DOCKER_SUBNET и HR_WEB_INTERNAL_IP, сохранив адрес внутри подсети. Остальные контейнеры не становятся доверенными прокси. API и PostgreSQL по-прежнему опубликованы только на loopback хоста.

При размещении за дополнительным HTTPS-прокси нужно отдельно настроить доверие Nginx к точному адресу этого прокси и получение реального клиента. Иначе remote_addr будет адресом внешнего прокси. Не доверяйте всем внешним X-Forwarded-For и не открывайте API в обход пограничной защиты.

### Обновление существующего локального Compose

Из-за изменения IPAM-сети для перехода с прежнего выпуска один раз остановите сервисы, сохранив bind-каталог PostgreSQL и .env:

```bash
docker compose down
make up
```

Не используйте очистку .local/postgres, docker system prune или замену ключей ради обновления. down без удаления данных не сбрасывает базу. Остановка кратковременно прерывает локальный доступ. На macOS не запускайте scripts/cloud_env.sh — он предназначен только для облачной машины Codex. При конфликте подсети сначала выберите свободные локальные значения.

## Кандидатский API

GET приглашения, чтение попытки/изображений, старт, сохранение и завершение используют общий серверный лимит: по умолчанию 600 запросов на IP за минуту. CANDIDATE_IP_LIMIT_PER_MINUTE задаёт значение 1–100000. Значение 0 не отключает защиту. Счётчики общие в PostgreSQL между API-процессами; в ключе SHA-256 адреса, без токена приглашения. При превышении JSON rate_limited и Retry-After: 60, попытка и ответы не изменяются. Неверные по синтаксису токены отклоняются до DB-счётчика; Nginx ограничивает также такие запросы.

Пограничный Nginx дополнительно ограничивает /api/v1/invite/ до 20 запросов/сек на адрес с burst 100, возвращая стандартный JSON 429. Эти параметры — защита от всплесков, не подтверждённый нагрузочный профиль. За офисным NAT пользователи имеют общий публичный IP; лимит нужно подобрать по испытаниям, а не обещать отдельный IP каждому человеку. Для распределённой атаки нужны инфраструктурные меры и мониторинг.

Давние технические счётчики всех типов удаляются существующим maintenance-worker раз в минуту, до 1000 строк старше суток. Активные окна не затрагиваются. Это служебная очистка, не пользовательская политика хранения. Миграция 0014 добавляет индекс для неё; предметных таблиц не добавлено, всего остаётся 36 с реестром. Readiness требует 0014.

## Актуальные административные права

Создание сотрудника, выдача приглашения и изменение роли/активности после блокировки организации заново проверяют живую сессию, пользователя, членство, роль org_admin и статус организации. Если права изменились во время ожидания, транзакция не применяется и возвращается 401. Используется та же серверная проверка, что в настройках/хранении/импорте. Защита последнего администратора сохраняется.

## Зависимости

happy-dom обновлён с 20.8.4 до 21.0.1 с фиксацией lock-файла. Повторный npm audit проверяет в том числе dev-зависимости; результаты записаны в validation.md. Добавлен npm audit --audit-level=high в GitHub Actions. Проверка не подавляет dev-уведомления и не выполняет автоматический npm audit fix. Новые Go-библиотеки не понадобились.

Нулевая выдача npm audit означает отсутствие известных уведомлений в полученной базе на момент проверки. Она не заменяет анализ Go-зависимостей, контейнеров, ОС и прикладной безопасности.

## Проверки и границы

Модульные проверки: доверенный/прямой/соседний источник, поддельные и множественные заголовки, IPv6/IPv4-mapped, неправильные конфигурации. DB/HTTP: создание/приглашение/изменение команды после отзыва роли во время ожидания, лимит GET/POST, отдельные клиенты за прокси, подделка заголовка напрямую, истечение минуты и сохранение активных счётчиков при уборке. Проверки используют только временные организации и известные тестовые IP.

RLS, полное индивидуальное удаление, обязательная MFA-политика, антивирус вложений, реальные письма, внешний backup, инфраструктурный мониторинг и промышленная нагрузка этим этапом не объявляются готовыми. Текущая версия по-прежнему предназначена для разработки и ограниченного тестирования.
