# Журнал аудита и хранение данных

Администратор организации видит разделы «Журнал аудита» и «Хранение данных». Рекрутер, оценщик и кандидат не получают эти API. Организация определяется сессией, а не запросом. Чужие/неизвестные ID предпросмотра и кандидата дают 404.

## Журнал

Журнал показывает сотрудника (или систему), действие, тип/ID объекта и время. Фильтры: действие, объект, сотрудник/система, календарные даты по МСК; конец диапазона включён. Страница — 50 записей, новые сверху; ID события передаётся строкой. Имя сотрудника берётся из текущего профиля, событие сохраняет его ID. Коды незнакомых действий показываются как есть.

Пароли, приглашения, контакты, содержание ответов и свободный текст причин не выводятся через details. Сервер допускает только известные безопасные поля формата/чисел/дат/флага запрета. Сырые details никогда не пересылаются в UI. Это не изменяет старые JSON в базе: историческое чувствительное содержимое, если оно было записано иным процессом, контролируется отдельно политикой и привилегированными средствами. Чтение журнала не создаёт рекурсивные события.

У app-role отозваны UPDATE/DELETE для audit_events. Удаление по сроку выполняет только prune_audit_events: SECURITY DEFINER с фиксированным search_path и явными public-таблицами, без динамического SQL, EXECUTE только для hr_app. Функция проверяет живую сессию именно администратора, автора/организацию/версию/срок предпросмотра, включённые правила и cutoff; удаляет только выбранные IDs своей организации старше cutoff. Владелец миграций остаётся привилегированной ролью; это не внешнее неизменяемое хранилище аудита.

## Правила

По умолчанию очистка выключена, сроки не заданы. Администратор указывает candidate_days и/или audit_days (1–36500 целых дней), цель и утверждённое основание, затем включает применение правил. Пустой срок оставляет этот тип данных вне очистки. Обновление защищено base_revision; старая версия даёт 409. Политика не является юридическим заключением: срок/основание устанавливает организация по своим обязательствам.

Автоматического расписания нет. Включение правил только разрешает подготовить и подтвердить ручную операцию; само по себе ничего не удаляет.

## Предпросмотр и применение

1. Сохранить правила, нажать «Подготовить предпросмотр».
2. Проверить имена выбранных кандидатов, количество старых событий и срок списка. Пакет ограничен 100 кандидатами/1000 событиями; следующую порцию можно обработать новым предпросмотром.
3. Ввести фразу «УДАЛИТЬ ПО ПРАВИЛАМ» и применить.

Список хранит только IDs, cutoff и версию политики, действует 15 минут и доступен для применения только создавшему его администратору. При изменении политики/истечении срока нужен новый список. Очистка проверяет права ещё раз после ожидания блокировок. Повтор одного предпросмотра возвращает сохранённую квитанцию, без повторных действий; новый после выполнения — новая операция.

Срок карточки считается от максимума created_at/updated_at, выдачи приглашения, старта/завершения попытки и записи согласия. День — 24 часа от момента предпросмотра. Уже очищенные карточки, erasure_pending, retention_hold, in_progress и действующие issued-ссылки исключаются. Перед применением проверка повторяется: новый контакт/приглашение/попытка/согласие или установленный запрет позволяют пропустить карточку. Записи, ставшие подходящими или появившиеся после предпросмотра, в пакет не добавляются.

Операция в одной транзакции:

- заменяет ФИО на «Контактные данные удалены», очищает email/phone, помечает erased_at и архив;
- отзывает все ссылки кандидата, очищает адреса связанных сообщений и отменяет pending/failed сообщения;
- удаляет записи согласий этого кандидата;
- сохраняет попытки, версии, выбранные варианты и итоговые баллы;
- удаляет выбранные старые события аудита и записывает новые события очистки/результата с исполнителем.

Карточку после erased_at нельзя редактировать, вновь активировать или пригласить через API/интерфейс. Это удаление контактных полей, не гарантированная полная анонимизация: UUID, результаты и административные связи остаются. Основания, требующие сохранить согласия/карточку, нужно защитить запретом очистки до выполнения.

Блокировки организации используют NO KEY UPDATE, совместимый с FK-операциями; приглашения блокируются прежде кандидата. Это позволяет запуску/сохранению/завершению попыток и выдаче приглашений завершиться и повлиять на повторную проверку, вместо удаления активного прохождения. Изменения правил и применение сериализованы; после ожидания проверяется актуальная сессия/роль. Привилегированное удаление аудита дополнительно проверяет сессию в БД.

## Запрет очистки

На карточке кандидата администратор может перейти к хранению данных и поставить запрет с причиной. Раздел показывает первые 100 запретов и позволяет их снять. Причина видна администратору, в аудит попадает только факт включения/снятия. Изменение запрета не продлевает срок искусственно: после снятия ранее просроченная карточка может попасть в следующий список.

## Границы этапа

Правила охватывают контактную карточку, согласия, адреса сообщений и старые события аудита в текущей БД. Они не очищают скачанные CSV/XLSX, резервные копии, внешние системы, тексты банка вопросов, аккаунты сотрудников и сохранённые попытки/ответы. Preview/result содержит только служебные IDs/счётчики; расписание удаления таких квитанций отдельно не добавлено. Обработка индивидуального запроса до истечения срока, полное удаление попыток, бэкапы и почтовая очередь — отдельные задачи. Политика реальных персональных данных/локализация/обязательное хранение требуют утверждения ответственным организации.

## Проверка

make check: Go tests/build/vet, Vue tests, TypeScript, Vite. make integration: две временные организации, реальные права app-role и удаление только фикстур. Проверены роли/tenant/CSRF, фильтры/allowlist, запрет обычного изменения/удаления аудита, выключенные defaults, валидация/конфликт политики, недеструктивный предпросмотр, активные/защищённые/чужие/свежие записи, истечение/смена правил/автор, изменение прав во время ожидания, повторная пригодность, подтверждение, параллельный повтор, сохранность баллов, удаление контактов/согласий/адресатов и аудит операции.

Playwright desktop/320 px проверяет журнал/фильтр экспорта, выключенные правила, запрет предпросмотра несохранённых настроек и установку/снятие запрета своей помеченной карточки. Правила реальной тестовой организации не включаются и очистка её карточек не выполняется. Vue-тесты проверяют блокировку очищенной карточки и отсутствие запросов изменения при submit; обычная карточка остаётся редактируемой.

Миграция 0009 добавлена без изменения 0001–0008. Контракт — OpenAPI 0.6.0. Рабочая ветка HR-TESTING; новые изменения этого этапа пока локальные.
