# Прохождение и подсчёт результатов

Кандидат открывает персональное приглашение, знакомится с правилами, отмечает согласие и нажимает «Начать тест». У теста одна страница прохождения: вопрос, варианты, таймер, переходы и номера заданий. Подтверждение завершения показывает число пропущенных вопросов. HR видит статусы и итоги в разделе «Результаты».

## Время и восстановление

- PostgreSQL задаёт started_at и deadline_at: минимум из времени старта + длительность опубликованной версии и срока приглашения.
- Таймер в браузере вычисляется по server_now и performance.now; изменение системных часов не продлевает попытку. Сверка с сервером каждые 5 секунд. Решение о принятии ответа принимает сервер.
- Порядок вопросов и UUID вариантов фиксируются в attempt_items при старте. Перемешивание использует crypto/rand. Три варианта verbal_tfu сохраняют определённый порядок.
- Каждый подтверждённый старт или восстановление связывает request_id с попыткой в start_receipts. Повтор возвращает ту же попытку, даже если она уже завершена. Пока есть активная, другой старт также возвращает её. Новая после завершения требует явного new_attempt=true, нового request_id, действительного приглашения и оставшегося лимита. Блокировка приглашения и уникальный индекс защищают от параллельных стартов.
- Перезагрузка сначала читает последнюю попытку; она не запускает новую. Возвращаются только подтверждённые ответы, постоянный порядок и прежний срок.
- Завершённую попытку можно восстановить по той же ссылке после её срока. Отзыв ссылки или архив кандидата/организации блокируют доступ. Для нового старта срок всегда проверяется.

## Автосохранение

Каждый выбор отправляется сразу. Запросы одного вопроса выполняются последовательно; быстрые изменения отправляют последнее выбранное состояние после подтверждения предыдущего. Ответ содержит selected_option_ids, expected_revision и UUID request_id.

Сервер проверяет принадлежность попытки приглашению, задания попытке, вариантов вопросу, уникальность выбранных UUID и число вариантов для single_choice/verbal_tfu. Пустой массив удаляет выбор. Сохранение атомарно увеличивает ревизию; чужая вкладка с устаревшей ревизией получает 409 revision_conflict, без перезаписи.

answer_receipts сохраняет квитанцию: потерянный ответ сервера можно получить повтором того же запроса без изменения ревизии. Прежняя квитанция подтверждает только прежнее сохранение; не даёт права менять завершённую попытку. Повтор UUID с другим содержимым отклоняется.

Надпись «Все изменения сохранены» появляется после подтверждения сервера. Вне сети остаются неподтверждённые изменения и сообщение об ошибке, повтор выполняется при восстановлении сети или кнопкой. При конфликте выбор блокируется; кандидат может явно загрузить сохранённые ответы. Неподтверждённые изменения хранятся только в памяти вкладки; после её закрытия/перезагрузки восстанавливается серверное состояние. Предупреждение при уходе зависит от поддержки beforeunload браузером.

Перед ручным завершением интерфейс ждёт сохранения. При ошибке не сообщает о завершении. По сроку отправляет завершение даже при несохранённых изменениях; сервер учитывает только принятые ответы.

## Оценивание

За вопрос начисляется полный вес только при точном совпадении множества выбранных и правильных вариантов. Пропуск, недостающий правильный или лишний неправильный вариант дают 0. Частичных баллов нет.

Суммы считаются в целых сотых балла; percentage = round(100 × earned / max, 2), passed сравнивает этот округлённый процент с порогом опубликованной версии. Например, 2.50 из 4.00 = 62.50%. При пороге 62.50 результат проходной. Правильный verbal_tfu весом 1.25 при ошибочном single_choice и неполном multiple_choice даёт 31.25%.

Ручное завершение до срока сохраняет submitted, после срока — expired. Повторное завершение не меняет баллы или finished_at. Проверка времени идёт после получения блокировок, через clock_timestamp; ожидание блокировки не позволяет отправить поздний ответ.

В процессе API работает обработчик просроченных попыток: сразу при старте процесса и каждые 2 секунды, пакетами по 100. Он использует те же блокировки invitation → attempt и транзакционный расчёт, поэтому работает без браузера, после простоя и в нескольких экземплярах API. При временной недоступности БД повторит обработку на следующем цикле. Финальное finished_at просроченной попытки равно deadline_at. Отзыв приглашения отменяет активную попытку; завершённые результаты сохраняются.

## Доступ и контракт

Все кандидатские пути находятся под /api/v1/invite/{token}; UUID попытки сам по себе не авторизует доступ. Изменения требуют разрешённый Origin. URL с секретом исключён из Nginx access log; для кандидатского API выключен error log, который иначе включает URL при недоступности upstream; безопасные ошибки приложения доступны в API log; установлен Referrer-Policy: no-referrer, no-store и noindex.

Отдельный DTO содержит вопрос/текст, ID и подписи вариантов, собственные сохранённые ответы, ревизию и время. В нём нет is_correct, explanation, весов, порога, контактов и идентификатора кандидата. Финальные items пусты; score (процент и passed) присутствует только после submitted/expired при включённом show_candidate_score.

GET /api/v1/results требует HR-сессию: org_admin/recruiter своей организации, assessor — только назначенные вакансии. Баллы в этой выдаче не зависят от кандидатского показа. Подробный отчёт, CSV/XLSX и категории уже добавлены; см. reports.md.

OpenAPI 0.4.0 описывает запуск, восстановление, сохранение, завершение и выдачу HR. Добавлены миграции 0006/0007, прежние миграции не изменялись. start_receipts фиксирует request_id также для восстановления: повтор такого запроса после завершения не создаёт новую попытку.

Согласие записывается в candidate_consents с purpose=test_passage, document_version=development-passage-v1 и ID попытки. Это правила тестового контура и фиксация действия, а не подготовленная политика обработки реальных персональных данных. Перед рабочим применением организация должна утвердить свой текст и версию.

## Проверка

1. Создать и опубликовать вопросы и тест, добавить кандидата и выдать ссылку.
2. Открыть ссылку без HR-сессии, принять правила, начать, выбрать ответ и дождаться подтверждения.
3. Отключить сеть, изменить ответ: сообщение должно показывать отсутствие подтверждения. Включить сеть, дождаться сохранения.
4. Перезагрузить страницу: выбранные ответы и порядок должны восстановиться, срок остаться прежним.
5. Завершить, затем открыть «Результаты» в HR-сессии. При выключенном показе кандидат не получает баллы.

Автоматизация: make check (Go/Vue/TS/build/vet), make integration (реальная PostgreSQL и негативные HTTP-сценарии), npm run test:e2e в frontend (desktop и 320 px). На запущенном локальном Compose make runtime-check перезапускает API и проверяет восстановление, затем ждёт фонового завершения через HR endpoint, без обращения к кандидатскому endpoint. Не применять эту проверку к рабочей базе.

При захвате браузерных/Playwright логов используйте файл с правами 0600 и маскируйте токены перед выводом: URL ошибок может содержать секрет приглашения. Пароли и ссылки не печатать.
