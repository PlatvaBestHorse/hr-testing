# Кадровый тестер Web 2.0

Основа платформы тестирования кандидатов по ТЗ: **Go + Vue 3 / TypeScript + PostgreSQL**.

## Что уже работает

- Русскоязычный адаптивный интерфейс: вход, обзор, команда, категории и редактор вопросов.
- Импорт CandidateTester JSON: предварительный отчёт, атомарный перенос вопросов/тестов и защита от повторов.
- Смена пароля, восстановление по почте и TOTP MFA с одноразовыми резервными кодами; локальная проверка писем без внешнего сервиса.
- Настройки организации, приглашения сотрудников и комментарии к завершённым результатам.
- Первая организация и администратор через CLI; пароли Argon2id, сессии в HttpOnly-cookie, CSRF и ограничение попыток входа.
- Серверные роли: администратор управляет командой, HR редактирует вопросы, оценщик не получает банк ответов. Организация берётся только из проверенной сессии.
- Категории, поиск и фильтры; три типа вопросов, предпросмотр, публикация, история редакций и архив.
- Опубликованные версии и варианты защищены от изменения триггерами PostgreSQL; параллельное сохранение контролирует номер исходной версии.
- Конструктор тестов: опубликованные вопросы, порядок, точные веса, время, порог, перемешивание и показ результата; неизменяемые публикации и новые редакции.
- Кандидаты и вакансии, назначение оценщиков, персональные приглашения со сроком и лимитом попыток, копирование и отзыв ссылок.
- Общедоступная страница приглашения без ключей ответов и контактов кандидата. Секрет ссылки выдаётся один раз; в базе только SHA-256 токена.
- Прохождение без аккаунта: серверный таймер, постоянный порядок заданий, автосохранение с ревизиями, повтор запросов и восстановление подтверждённых ответов.
- Завершение по кнопке или времени, точный подсчёт весов и процентов. Фоновое завершение работает без браузера и после перезапуска API.
- Журнал аудита администратора: фильтры, безопасные метаданные; правила хранения, предпросмотр и подтверждённая очистка контактных данных/старого аудита, запреты очистки.
- Раздел результатов для HR; оценщик видит назначенные вакансии. Кандидат видит баллы только при включённом показе в опубликованной версии теста.
- Go API с проверкой работоспособности, готовности базы, идентификаторами запросов и корректным завершением.
- 20 предметных таблиц из предоставленной SQL-схемы, составные связи внутри организации.
- Транзакционные миграции с блокировкой параллельного запуска, контрольными суммами и повторным запуском.
- Отдельные роли владельца миграций и приложения, локальные уникальные пароли вне Git.
- Docker Compose, модульные и интеграционные проверки, браузерные проверки и GitHub Actions.

Это приложение в разработке. Кандидат может начать тест, восстановить сохранённые ответы и завершить попытку; HR видит рассчитанные итоги. Работают подробный разбор ответов, итоги по категориям, фильтры и CSV/XLSX. В облачной машине подготовлен отдельный тестовый администратор; промышленные учётные записи и реальные данные кандидатов не используются. Текст согласия версии development-passage-v1 предназначен для тестового контура; перед реальным применением требуется политика организации.

## Запуск через Docker

Нужны Docker Engine с Compose v2, Python 3 и Make. Выполнять из корня репозитория:

```bash
make up
```

Команда создаёт `.env`, запускает PostgreSQL, применяет миграции отдельным процессом, запускает API и интерфейс. `.env` не перезаписывается. Настройки портов — в `.env`: интерфейс 8088, API 8080, база 5432. Порты доступны только на машине разработки.

```bash
make down       # остановить сервисы; данные сохраняются
```

Данные PostgreSQL хранятся в игнорируемой папке `.local/postgres`. Не удаляйте её и не меняйте пароль существующей базы только через `.env`: это не меняет пароль роли в PostgreSQL. Для проверки изменения пароля нужна отдельная административная операция.

Для Linux cloud runner с предоставленным сетевым прокси используйте дополнение конфигурации:

```bash
. scripts/cloud_env.sh
make up
```

Подробности конкретной облачной среды: [docs/cloud.md](docs/cloud.md).

## Первый администратор и вход

После установки Go-зависимостей и запуска базы с миграциями выполните из корня:

```bash
make admin
```

При работе только через Docker Desktop, без Go, после `make up` используйте вместо этой команды:

```bash
make admin-docker
```

Команда спросит организацию, имя, почту и пароль без его отображения. Создаёт первую организацию и администратора атомарно; повторное создание на существующей базе запрещено. Новый сотрудник добавляется администратором в разделе **Команда**. Публичной регистрации организаций и сотрудников нет.

Только для локальной разработки:

```bash
make admin-dev
```

Это создаёт `admin@local.test` с уникальным случайным паролем. Данные находятся в `.env.admin.json` (0600, исключён из Git), пароль в вывод команд не попадает. Файл создаётся перед bootstrap; существующий файл не перезаписывается. Эта команда не предназначена для промышленной базы и отказывается работать при внешнем `DATABASE_URL`. Если файл существует, а bootstrap раньше не завершился, восстановите именно эту локальную тестовую учётную запись по инструкции в `docs/auth-and-questions.md`.

В браузере используется `/login`. Через интерфейс можно добавить категории, сохранить вопрос, опубликовать его, открыть прошлую версию и создать новую редакцию. Каждый запрос к данным проверяет роль и организацию на сервере; значения `organization_id` из тела запроса не принимаются.

В локальном Compose явно задано `COOKIE_SECURE=false` для loopback HTTP. Для HTTPS-размещения задайте `COOKIE_SECURE=true` и `APP_ORIGINS=https://ваш-домен` без пути и завершающего `/`. Cookie-сессия действует 8 часов; токен хранится в базе только как SHA-256. CSRF-токен остаётся в памяти интерфейса, session cookie недоступна JavaScript. В production потребуется HTTPS; не переносите локальные HTTP-настройки.

## Разработка с быстрым обновлением

Нужны Go **1.26.9**, Node.js **24**, npm, Docker Compose, Python 3 и Make.

```bash
make install
make db
make migrate
```

В двух отдельных терминалах, из корня репозитория:

```bash
make api
```

```bash
make web
```

Vite использует порт 5173 и проксирует `/api` в Go API на порту 8080. Для другого API-порта измените также proxy target в `frontend/vite.config.ts`. Сервер API по умолчанию слушает только loopback; контейнерный режим задаёт `HTTP_ADDR=0.0.0.0:8080`.

`scripts/run_backend.py` читает локальную `.env`, не выводя пароли. Внешнее подключение можно задать через `DATABASE_URL`; для API используйте ограниченную роль `hr_app`, для миграций — владельца схемы. Локальный `sslmode=disable` относится только к контуру разработки; для удалённой базы требуется проверяемое TLS-подключение.

## Проверки

```bash
make check                # Go tests/vet/build, Vue tests/typecheck/build
make db migrate integration  # реальная база: миграции, роли, tenant-FK
```

Обычный `go test ./...` пропускает DB-интеграционные тесты без специальных переменных. `make integration` выполняет тест ограниченной DB-роли и полный HTTP-сценарий на локальной базе. Временные организации HTTP-теста удаляются по их идентификаторам отдельной транзакцией привилегированной тестовой роли; обычный app-role не может обходить защиту опубликованных версий. Не направляйте тесты на промышленную базу.

После `make up` и `make admin-dev`, из `frontend`:

```bash
npx playwright install --with-deps chromium
npm run test:e2e
```

Можно использовать уже установленный Chromium: задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`. Для проверки Vite вместо контейнерного интерфейса задать `E2E_BASE_URL`. Браузерные тесты проверяют вход, банк вопросов и конструктор, публикации и версии, вакансии/кандидатов, выдачу ссылки, прохождение без HR-cookie, отключение сети, автосохранение, восстановление после перезагрузки, завершение и баллы HR, меню на 320 px и выход. В тестовой организации остаются явно помеченные вопросы/категории проверки; вопросы переводятся в архив.

## Структура

```text
backend/cmd/api/             сервер
backend/cmd/migrate/         запуск миграций владельцем схемы
backend/internal/           конфигурация, база, HTTP API
backend/migrations/         встроенные в бинарник SQL-миграции
frontend/src/               Vue-интерфейс
frontend/e2e/               браузерные проверки
infrastructure/postgres/    создание ограниченной DB-роли
docs/reference/             исходные ТЗ, архитектура и SQL без изменений
docs/openapi.yaml           контракт реализованных API
```

## Статусы и следующие этапы

Актуальная карта: [docs/roadmap.md](docs/roadmap.md). Локальные контейнеры и страница входа на Mac пользователя запущены; создание администратора и ручной вход ещё требуют подтверждения. Один сайт может обслуживать несколько компаний, но штатное подключение второй организации ещё не реализовано.

Завершены [исправления безопасности после аудита](docs/security-hardening.md) и подготовка [серверной конфигурации с HTTPS](docs/production.md). Отдельный Compose-контур, данные/ключи вне исходников, образ оператора и перезапуск проверены на синтетической базе. Внешнего сервера и публичного домена пока нет. Следом:

1. Индивидуальное удаление и рабочая политика персональных данных.
2. Реальная почта, внешние резервные копии, мониторинг и автоматическое развёртывание.
3. Выбор сервера/домена, настройка TLS и пилот одной компании после проверок.
5. Перед SaaS — создание/переключение организаций, дополнительная изоляция и квоты.

Сейчас RLS не включён: составные FK проверяют связи, чтение ограничивается серверными запросами с организацией из сессии. Проверены негативные cross-tenant HTTP-сценарии. Для новых API такие проверки обязательны. Предоставленный JSON-банк CandidateTester version 1 поддержан; тип single. Другие старые форматы, вербальные наборы и данные прежних прохождений потребуют отдельных образцов и сверки. Подробности реализованного этапа: [docs/auth-and-questions.md](docs/auth-and-questions.md).

Промышленный запуск потребует HTTPS, рабочих настроек доступа и почты, политики персональных данных, внешнего резервного копирования и испытаний из ТЗ. Текущий Compose предназначен для разработки.

Конструктор и приглашения: [docs/tests-and-invitations.md](docs/tests-and-invitations.md).

Прохождение и подсчёт результатов: [docs/attempts.md](docs/attempts.md). Дополнительная проверка на запущенном локальном Compose — `make runtime-check`: перезапускает API, проверяет восстановление и фоновое завершение без браузера; использует только тестовый контур и оставляет помеченные записи.

Резервные копии базы: `make backup` создаёт зашифрованную копию и проверяет реальное восстановление в отдельную базу; `make backup-verify` повторяет проверку. Хранение и восстановление описаны в [docs/backups.md](docs/backups.md). Ключ и копии исключены из Git; независимое внешнее хранение пока не подключено.

Подробные отчёты и экспорт: [docs/reports.md](docs/reports.md).

Аудит и правила хранения: [docs/audit-and-retention.md](docs/audit-and-retention.md). Очистка по умолчанию выключена; утверждённые сроки задаёт администратор.

Изображения вопросов и вариантов: PNG/JPEG в редакторе, прохождении и веб-отчёте, с проверкой доступа и сохранением истории. Они входят в копию PostgreSQL. Форматы, ограничения и API — [docs/images.md](docs/images.md).

Пароль, MFA и почта: [docs/account-security.md](docs/account-security.md). `make init` создаёт отдельный ключ шифрования аккаунтов; сохраните его защищённую копию отдельно от базы. Локальные письма в `.mailbox` исключены из Git.

Настройки, сотрудники и комментарии: [docs/administration.md](docs/administration.md).

Импорт старого банка: [docs/legacy-import.md](docs/legacy-import.md), [отчёт по предоставленному файлу](docs/import-sample-report.md). Предварительная проверка не меняет банк; перенос требует отдельного подтверждения.
